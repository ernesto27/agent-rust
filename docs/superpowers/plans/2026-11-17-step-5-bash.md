# Step 5 Bash Tool Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the streaming REPL run bash tool calls and answer from their results.

**Architecture:** Extend the existing Chat Completions client with indexed tool-call accumulation and a sequential agent loop. The added behavior will exceed roughly 300 lines in main.rs, so extract wire types, HTTP/stream handling, and bash execution into focused modules within the existing crate. Keep the REPL and tool loop together in main.rs.

**Tech Stack:** Rust edition 2024; existing Tokio, reqwest, serde, serde_json, anyhow, futures, eventsource-stream; standard-library pipes. No new dependencies.

**Spec:** [Approved Step 5 design](../specs/2026-11-17-step-5-bash-design.md), extending [SPEC-chat-loop.md](../../../SPEC-chat-loop.md) and [PLAN.md Step 5](../../../PLAN.md#step-5-tool-plumbing--bash).

## Global Constraints

- "Use the existing Rust 2024 binary crate and dependencies; no provider abstraction, workspace, permissions layer, or additional tools."
- "Execute nothing until the entire stream is complete and the batch has been validated."
- "Arguments remain the exact accumulated JSON **string** in conversation history."
- "Assistant text alone remains on stdout."
- "No live provider or paid calls are necessary."
- "Mark Step 5 items complete only after behavior is verified."
- Keep existing configuration, prompt, REPL, first-choice policy, usage handling, and fail-fast streaming behavior.
- Preserve unrelated changes to software-factory.json and untracked SPEC-streaming.md.
- Step 6 owns timeouts, process groups, model-output truncation, error prefixes, and malformed-argument recovery.

## Review Focus

Five easy-to-miss conditions, with tests assigned below:

1. A valid first call followed by an invalid second call must execute neither (Task 3).
2. Pipe-sized output must drain while the child runs, avoiding a wait-before-read deadlock (Task 2).
3. A command reading stdin must see EOF without consuming a queued user turn (Tasks 2 and 3).
4. Signal termination and invalid UTF-8 output must produce a usable tool result (Task 2).
5. A Unicode preview must respect both caps without shortening model-visible output (Tasks 2 and 3).

## File Responsibilities

- `src/main.rs`: configuration, startup prompt, input loop, sequential tool round loop.
- Create `src/types.rs`: ChatMessage, ToolCall, FunctionCall, BashArgs, CompletedReply.
- Create `src/openai.rs`: typed request/schema/chunks, HTTP/SSE client, accumulation and complete-batch validation.
- Create `src/bash.rs`: process execution, merged capture, status serialization, stderr preview.
- `tests/chat_loop.rs`: reuse the existing HTTP mock and subprocess helpers; extend their fixtures for tool calls. Unit tests live beside private accumulator/executor helpers.
- Documentation: this plan, the approved design, SPEC-chat-loop.md, PLAN.md. Do not change Cargo.toml/Cargo.lock unless a verified implementation need requires an approved scope change.

### Task 1: Typed tool protocol and complete streamed replies

**Files:** Create `src/types.rs`, `src/openai.rs`; modify `src/main.rs`; extend `tests/chat_loop.rs`.

**Interfaces:**
- `ChatMessage { role: String, content: Option<String>, tool_calls: Vec<ToolCall>, tool_call_id: Option<String> }` derives Serialize/Deserialize; default/omit empty tool_calls and omit absent tool_call_id.
- `ToolCall { id: String, kind: String, function: FunctionCall }`, with kind renamed to `type` in serde.
- `FunctionCall { name: String, arguments: String }`; `BashArgs { command: String }` derives Deserialize.
- `CompletedReply { message: ChatMessage, commands: Vec<BashArgs> }` contains validated arguments in exactly message.tool_calls order.
- `pub async fn chat(client: &reqwest::Client, url: &reqwest::Url, api_key: &str, model: &str, history: &[ChatMessage], stdout: &mut impl std::io::Write) -> anyhow::Result<CompletedReply>` in openai.rs.
- Private `ToolAccumulator::push(delta: ToolCallDelta) -> Result<()>` and `finish(self) -> Result<(Vec<ToolCall>, Vec<BashArgs>)>` in openai.rs; use BTreeMap<usize, PartialToolCall> and a set for id uniqueness.

### Task 2: Bash execution with shared capture and bounded preview

**Files:** Create `src/bash.rs`; add module declaration to `src/main.rs`.

**Interfaces:**
- Consumes `types::BashArgs` indirectly via its command string.
- `pub async fn run(command: &str, cwd: &std::path::Path, stderr: &mut impl std::io::Write) -> anyhow::Result<String>` returns the serialized tool-result content.
- Private `fn preview(output: &str) -> (String, bool)` returns capped text and whether anything was omitted.

- [ ] **1. Write failing tests** using throwaway directories and a Vec<u8> diagnostic writer. For `printf out; printf err >&2; exit 7`, deserialize the returned string and assert:

  ```rust
  assert_eq!(result["output"], "outerr");
  assert_eq!(result["exit_code"], 7);
  assert!(diagnostics.starts_with("$ printf out; printf err >&2; exit 7\n"));
  ```

  Also cover empty command success, cwd via pwd, `cat` seeing EOF, `printf '\377'` yielding U+FFFD, and `kill -TERM $$` producing null exit_code with nonempty termination. Test more than a pipe buffer of output under a bounded test timeout. For preview, assert 10 lines and 2,000 Unicode scalar values maximum, no omission for exact limits, and omission for either exceeded cap. A failing stderr writer must return a contextual error before execution; verify with an absent marker file in the throwaway directory.
- [ ] **2. Run** `cargo test --locked --bin agent bash::tests` and confirm the new cases fail before implementation.
- [ ] **3. Implement** run using `std::io::pipe()`, cloned writer handles assigned to child stdout/stderr, Tokio Command with `-c`, the command as one argument, explicit cwd and null stdin. Start a `spawn_blocking` reader before awaiting child exit; drop parent writer handles and the configured Command after spawn so EOF can arrive. Await capture and child status, decoding lossily and serializing the full result. Include termination only when exit_code is null. Add contextual errors for pipe, clone, spawn, wait, capture, serialization and diagnostic writes/flushes. Do not alter the shell command with quoting wrappers or redirects.
- [ ] **4. Implement** preview with both limits, preserving Unicode boundaries, and add an explicit omission note only when shortened. Flush the command before spawn; after completion emit status and preview to stderr. Keep the full result content separate from its preview.
- [ ] **5. Run** `cargo fmt --check` and `cargo test --locked --bin agent`. Expected: all unit tests pass with no pipe deadlock; zero-exit results have no termination field. Existing integration tests still pass with `cargo test --locked --test chat_loop`.
- [ ] **6. Commit** only Task 2 files with message `feat: execute bash with merged output and status`.

### Task 3: Sequential tool rounds and end-to-end verification

**Files:** Modify `src/main.rs`, `tests/chat_loop.rs`, `SPEC-chat-loop.md`, `PLAN.md`; update status in the design doc after verification.

**Interfaces:**
- Consumes `openai::chat(...) -> Result<CompletedReply>` and `bash::run(command, cwd, stderr) -> Result<String>`.
- The input loop owns history; the inner tool loop appends completed assistant messages and one tool message per call, preserving ids and ordering. No new public API is required.

- [ ] **1. Write failing subprocess tests** using the Task 1 tool fixtures and existing run/run_with_handshake harness:
  - `bash_round_replays_exact_history`: call `printf hi`, then final text, then a second user turn; assert exact assistant tool_calls, null content, JSON-string arguments, tool_call_id/result content, final assistant text and next user message. Assert stdout contains only the two final answers and stderr contains command/status/preview. Every request advertises the same tool.
  - `multiple_calls_and_rounds_execute_in_numeric_order`: first call creates a marker, second reads it; fragments arrive in reverse index order. Then request another tool round before a final answer. Assert one tool message per call and no extra user message or prompt between rounds.
  - `mixed_text_and_tool_only_responses`: preserve streamed explanatory text and its success newline; tool-only replies emit no stdout newline. Exercise fragmented escaped arguments across network writes and optional usage after tool_calls finish.
  - `invalid_batch_never_executes`: valid marker-writing call first, invalid call second. Cases include malformed args, missing command/id/type, duplicate id, unknown name, conflicting metadata, wrong finish reason, missing finish reason, missing `[DONE]`, malformed trailing SSE/JSON. Assert nonzero exit, no next API request, no command diagnostic and no marker. Extend the harness with an internal inspection callback before TestDir drops, preserving existing callers.
  - `nonzero_exit_returns_to_model`: command exits 7; assert result contains exit_code 7 and the model gets a follow-up request and can answer successfully.
  - `tool_stdin_does_not_consume_next_turn`: queue two user lines; first tool runs cat; assert it returns empty output and the second user line is submitted normally.
  - `preview_is_bounded_but_result_is_complete`: output exceeds both caps using Unicode; assert full output in the next request, bounded preview plus omission note on stderr, and clean assistant stdout.
  - `failure_after_a_tool_round_stops_queued_input`: HTTP/stream failure on follow-up preserves previous text but sends no queued user turn.

- [ ] **3. Break on zero calls. Never prompt or read user input between rounds. Propagate fatal errors immediately without fabricated results or retries.

## Plan Self-Review

Spec coverage: protocol/schema/assembly and whole-batch validation → Task 1; process/stdin/merged output/status/previews → Task 2; history/loop/multiple turns, failure behavior and acceptance smoke check → Task 3. All five Review Focus conditions have explicit tests. No new tools, provider interfaces, dependencies, timeout policies or recovery paths are planned.

Execution choice remains with the user. Native execution is recommended because these three tasks share a small, sequential set of interfaces and one existing integration harness.
